# 代码结构与复用审查

从算例整体职责与数据所有权的角度审查改动或当前代码，先给出 findings。
重点是新增或加重的维护负担，而非一般 bug 扫描。不修改源码、配置、规则或记忆，
不执行重构；唯一的写操作是向 `<case>/docs/structure_review_log.md` 追加本次记录并
只提交该文件。findings 由用户另开开发任务处理。

## 确定审查对象

先检查 `git status`。审查对象是已提交代码，工作区未提交修改不纳入，存在时在报告中
说明。按以下优先级确定模式：

1. **用户指定范围**：用户给出提交区间、路径或要求审查工作区时照做，不写审查记录，
   除非用户要求。
2. **增量审查（默认）**：读取 `<case>/docs/structure_review_log.md` 最后一条记录的
   目标提交作为基线 `B`，审查 `B..HEAD` 在该算例目录内的累计改动。
   - 用 `git log --oneline B..HEAD -- <case>` 和 `git diff -M --stat B..HEAD -- <case>`
     了解改动主题；`--diff-filter=A` 找新增文件；按文件和函数分组审查，优先看
     新增函数、新文件、新状态和替代路径。
   - 累计 diff 只用于定位改动点。判断是否重复时比较的是改动点与算例当前全部代码，
     不是与 diff 内部比较。
   - 区间内先加后删、已被回退的改动不报告；以 `B` 与 `HEAD` 的实际差异为准。
   - `B` 不是 `HEAD` 的祖先（历史被改写）时，说明情况并改用整体审查。
   - 无改动时追加一条“无改动”记录即可。
3. **整体审查**：算例无审查记录、用户要求整体审查，或增量审查发现问题集中且需看
   全局时，审查该算例 `src/` 的当前全部代码，建立基线。可先运行
   `scripts/code_audit.sh` 获取重复片段和未调用函数线索，再按下文逐项语义核对。

上次记录中“有意保留”和“待确认”的条目是已知状态：前者不再作为新 finding 报告，
后者在本次重新核对并给出结论或继续保留。

## 搜索与语义核对

1. 从 diff（整体审查时从各源文件的主要职责）定位新增或改写的入口、逻辑、配置、状态和抽象，追踪实际调用者、被调用者、
   数据来源与生命周期。阅读对应构建清单、输入配置或注册点，确认代码如何生效。
2. 用 `rg` 搜索目标模块及其实际依赖中的相近功能；必要时扩大到共享组件、相近算例
   或相关上游 API。默认排除构建产物、日志、运行数据和无关第三方版本，说明实际覆盖范围。
   “仓库整体视角”不要求逐文件通读，也不意味着跨算例应当共用一个实现。
3. 核对输入输出、前置条件、默认值与覆盖顺序、读写范围、阶段顺序、副作用、
   状态更新及失效机制。AMR/OSI 相关实现还须区分 level、phase、DDF 布局、
   valid/covered/interface/ghost 范围和通信语义。
4. 判断新实现应复用、扩展还是保持独立；检查替代路径是否遗留配置入口、调用者、
   状态或已过时的说明。提出最小范围建议，而不是完整重构方案。

重点检查：

- **重复逻辑**：同一概念职责另写算法、流程或参数处理，后续需要同步修改。
- **重复状态**：相同事实有多个可写来源，或缓存、派生状态缺少更新与失效机制。
- **并行实现**：新旧路径同时存在却没有明确模式、调用边界和退出理由。
- **无必要的包装或抽象**：单纯转发、改名或推测未来扩展，增加间接层与维护成本。
- **职责重叠**：多个函数或类争夺同一流程、资源、配置或生命周期的所有权。
- **未复用现有机制**：重建已有基础设施，或增加本可由现役通用路径支持的特殊分支。

## 合并建议的证据门槛

仅当片段承担同一概念职责、语义兼容且预期共同演化时建议合并。不要仅为 DRY 合并。
函数名、文本相似度和静态工具告警只能提供线索，不能证明职责或行为等价。

独立数值 oracle、不同物理模型、CPU/CUDA 后端、手动诊断和框架回调可能有保留理由。
说明其边界；不强迫它们共用会削弱验证独立性或改变数值顺序的实现。
无法核实等价性或维护后果时列为待确认候选，不作为已确认 finding。
无关历史重复单独记录，不要求当前任务顺带修复。

需要量化时可使用仓库已有的 `scripts/code_audit.sh`（若存在），报告输出到临时目录；
工具缺失时记录限制，不自动安装、修改配置或运行生产作业。该工具是可选线索，
重复率下降、编译通过和 checksum 相同不能替代语义核对或阶段逐值验证。

## 审查记录

在 `<case>/docs/structure_review_log.md` 末尾追加一条，不改写旧记录；文件不存在时
新建并加一行标题。每条记录包含：

```markdown
## YYYY-MM-DD
- 模式：增量 / 整体 / 无改动
- 基线：<B 的短哈希或“无”>　目标：<HEAD 短哈希>
- 覆盖：审查的文件或模块；未覆盖部分及原因
- code_audit（如运行）：重复率、复杂度报警数、未调用候选数
- 已确认：<编号. 标题 — 文件位置>（无则写“无”）
- 待确认：<同上>
- 有意保留：<条目及保留理由>
```

记录写完后只暂存并提交该文件，提交信息写明算例与目标提交。
该文件是审查基线的唯一来源，不在其他位置另记基线。

## 输出

先给已确认 findings，按维护影响排序。每项包含：

- 严重程度与简短标题，区分本次新增、加重和历史遗留。
- 当前改动与已有实现的准确文件位置，以及相关调用关系或状态所有权证据。
- 为什么是同一职责或冲突的事实来源，可能导致的具体维护后果。
- 最小处理建议、保留独立实现的必要边界，以及修复后需要的验证。

随后简要列出待确认候选、有意保留的并行实现，以及审查基线、覆盖范围与限制。
没有已确认问题时明确写“未发现已确认的结构问题”，不为凑 findings 提出抽象。
未完整搜索仓库或未运行数值检查时，不声称全仓无重复或实现数值等价。

调用示例：

```text
$review-code-structure 定期审查 BOX3D_OSI
$review-code-structure 对 Cylinder3D 做整体审查
$review-code-structure 审查 a1b2c3d..HEAD 的 BOX3D_OSI 改动，不写记录
```
