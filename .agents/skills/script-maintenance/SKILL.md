# 脚本生命周期管理

维护辅助脚本的长期可用性和科研复现能力。日常新增约束由仓库规则负责，
本 Skill 负责集中审查与经确认的实施，不以减少文件数为目标。
第一版直接使用现有搜索和检查工具，不开发扫描器、自动评分或自动清理程序。

## 范围与模式

- 先读生效的 `AGENTS.md` / `CLAUDE.md`、根 README 及目标范围的直接相关说明。
  本仓库脚本归属以[根 README](../../../README.md#脚本归属与生命周期)为准。
- 用户指定路径时按指定范围；否则沿用当前明确的算例。无法确定对象时先澄清，
  不自行扩大到全部算例、第三方 AMReX 或整个工作区。
- `Audit` 为默认模式：只读分析，报告直接回复用户，不写报告文件、不提交 Git。
  如用户另外要求保存报告，只写指定报告，不顺带实施建议。
- `Execute` 仅执行用户确认的具体维护方案。确认须能对应文件、操作与目标位置；
  已确认的条目不重复询问，新增或扩大的操作先补充报告并取得确认。
  泛泛的“整理一下”不视为批量删除或重构的授权。

## Audit：审查

1. 检查 `git status`、相关已暂存与未暂存 diff，区分现有修改和本次候选。
   覆盖目标范围内的已跟踪与未跟踪脚本；使用 `rg --files`、`git ls-files` 等，
   说明忽略文件、动态调用或范围限制带来的盲区。
2. 盘点现有入口、辅助模块、测试及一次性脚本。既检查 `scripts/temporary/`、
   `scripts/persistent/`（若存在），也检查平铺的 `scripts/`、`data_post_processing/`、
   算例根目录及已知实验目录；不能假定旧脚本已按生命周期分类。
3. 对候选说明职责、输入输出、依赖、运行环境、默认参数、写入或提交作业等副作用，
   以及关联的作业、图表、报告或实验。追踪 shell 的 source/exec、Python import/subprocess、
   调度入口、构建配置、测试、文档和直接相关的运行记录；不执行未知脚本来探测功能。
4. 在目标范围及实际依赖中比较功能，必要时只读参考公共工具或相近算例。
   文本相似仅作线索；核对数值定义、数据选择、归一化、MPI/资源配置和输出契约后，
   再判断参数化、扩展已有工具或保持独立是否合适。
5. 对范围内每个脚本给出下表分类；同时标注其角色（用户入口、内部依赖、验证驱动、
   实验预设或历史复现）和维护状态（现役、进行中、历史或未知）。角色不等于状态：
   “可以独立运行”“有独立功能”“曾通过验证”均不足以证明应继续作为现役入口。
   范围过大时明确未评估文件，不能用“其余保留”代替逐项结论。

| 分类 | 判断与建议 |
|---|---|
| KEEP | 有当前调用者、明确现役文档或正在进行的任务支撑；写出证据和保留位置。保留内部依赖不意味着增加用户入口 |
| PROMOTE | 具有实际长期需求，可形成稳定接口；给出目标入口、需参数化部分及验证方式 |
| MERGE | 与已有工具职责和语义兼容；指定承接工具、保留行为和旧入口的处理方式 |
| ARCHIVE | 退出日常入口但仍承载复现价值；列出归档位置和可复现所需材料 |
| DELETE | 功能已承接或用途确已结束，且复现材料足够；列出依据和待确认删除路径 |
| REVIEW | 用途、调用者、归属或等价性证据不足；说明缺少什么，不提前判为过时 |

长期价值看真实复用需求、接口稳定性和维护责任，不以脚本长度、年龄、提交时间或调用次数
单独决定。仅参数不同的实验优先保留配置及精确命令；不同物理判据、独立数值对照或
后端实现不能为消重而失去独立性。“未搜到引用”不证明无人使用，仍需检查文档命令、
动态路径和已知手动实验用途。只有语义兼容且存在实际共同维护需求时才向仓库根提取。

## 形成整个范围的收敛方案

先给出目标职责与布局，再安排可验证的实施批次，不能只选几个易合并的小文件就结束审查。
日常入口、内部支持、现役验证和历史实验应可区分；沿用项目既有目录约定，
不为了显得整齐创建一套并行入口或空目录。

- KEEP 和 REVIEW 都须逐项解释：KEEP 说明当前需求；REVIEW 说明已查证据、剩余问题和
  解除待决所需条件，不能以“可能有用”无限期默认现役。
- 对被新流程覆盖的专项入口指出承接关系及未覆盖差异。仍有历史复现价值时可以建议退出
  日常入口并归档；缺失输入或依赖是复现缺口，不能直接推出可删，也不能据此宣称归档后可运行。
- 列出精确源路径、目标位置、受影响调用者、验证方式与实施顺序；移动前检查相对路径、
  source/import、调度工作目录和权限。需要修复路径的归档也属于修改，不能按机械搬运跳过验证。
- 分别统计顶层脚本数、用户入口数和整个范围内脚本总数的前后变化。归档和移动只改变位置，
  不能报告成消除了重复功能；合并后的新增文件、配置及兼容层也要计入维护成本。

## Execute：实施与验证

1. 核对已确认清单与当前文件状态；若文件已变化，重新评估受影响条目。
   不覆盖用户现有修改，不扩大到求解器核心或无关算例。
2. 改动前保存代表性输入、精确调用参数和基准输出，明确可接受差异。
   优先扩展现有入口；只在明确职责或生命周期边界需要时提取模块，
   不为换名、统一目录或推测未来复用添加 wrapper。
3. 实施获批的整合、晋升或迁移，同步调用者、路径解析、调度器工作目录、权限、
   文档和相关测试。明确旧入口是继续兼容、转为历史复现入口，还是获批删除。
4. 按行为选择验证：shell 语法检查、适当的帮助/参数检查、小样本回归及路径检查。
   数据分析或绘图变更使用仓库根 `.venv/bin/python`，比较关键数据、指标和采样定义；
   仅图片存在或脚本退出成功不足以证明等价。ParaView 数据读取沿用其既有执行环境。
   不为了验证辅助脚本启动昂贵的 CFD 计算或提交作业，除非用户已明确授权。
5. 对归档或删除项确认复现链：源数据位置、步数、代码版本、环境依赖、命令参数、
   参考数据来源，以及归一化和容差定义。归档脚本要么保持可运行，要么记录历史工作目录
   和恢复方法；仅说“Git 可找回”不算完整复现证据。
6. 验证承接功能后重新检查引用，再删除获批路径。依赖不明、验证失败或需要额外昂贵运行的
   条目保留原文件并列为待处理；完成不受阻的获批条目，不把未验证结果报告为等价。
   不顺带删除 `runs/`、日志、检查点、图表或原始数据，也不把临时目录当成可整目录清空的授权。
7. 更新所属范围的 README 工具索引；已有 `persistent/README.md` 时按其约定维护，
   不另建重复索引。变更记录和 Git 提交遵循当前用户指令及仓库规则：本仓库实质性变更
   验证后写入相应 `docs/ai_changes/`，按规则仅提交本次修改，不推送远端。

## 维护报告

审查报告包含：

- 实际覆盖范围、脚本总数与六类统计；未逐项检查的文件单列为未评估，不混入分类数字。
- 逐文件表：路径、角色与维护状态、分类、理由和证据、目标工具或位置、受影响调用者。
- 整个范围的目标布局和数量变化；每批解决什么、剩余哪些条目，不把局部实施报告为整体清理完成。
- 重复功能和保留差异、科研复现风险、可执行的验证方案及证据盲区。
- 待用户确认的具体操作清单；将删除、迁移和接口变化逐项写清楚。

实施报告包含已完成条目、验证结果、实际删除或归档路径，以及保留未动的条目和原因。
报告本次授权与证据边界，不宣称完成未覆盖的算例或实验验证。
